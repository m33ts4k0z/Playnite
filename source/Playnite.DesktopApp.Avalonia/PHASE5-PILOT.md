# Phase 5 Avalonia Desktop pilot

This project is a side-by-side Desktop shell. It opens the same `Playnite.Core` database as the Fullscreen pilot and uses the Phase 3 loose-theme runtime. It does not replace or modify `Playnite.DesktopApp`; the WPF application remains the production Desktop path.

Run the real library with `Playnite.DesktopApp.Avalonia.exe`, optionally using `--userdatadir`, `--library-path`, or `--theme`. Run the isolated contract harness with `--self-test`; it creates and removes a temporary 1,000-game Core database and validates 74 Desktop contracts. `--plugin-compatibility-test` audits every extension in the selected user-data directory, exercises the injected SDK API plus advertised settings and metadata surfaces, writes `installed-plugin-compatibility.txt`, and exits nonzero for any load or contract failure. That mode disables tray behavior and settings persistence but opens the selected library and extensions normally, so it should be run against a disposable profile clone.

The current Phase 5 tranche includes virtualized grid and list views, Core filter presets, search, installed/favorite filters, sorting, flat virtualized grouping, selection-driven details, persisted Desktop settings, plugin loading, real play/install/uninstall orchestration, notifications, and synchronous Avalonia dialogs. Avalonia 12 custom chrome supplies native drag and caption-button roles, saves normal bounds/maximized state, and exposes notification-area, minimize-to-tray, and close-to-tray settings. The native tray menu is rebuilt from the live library with recent and favorite game launch actions, restore, co-located Fullscreen launch, and explicit exit. Its native metadata editor validates and persists the legacy writable `Game` field surface through `GameDatabase`: names and dates; user/critic/community scores; descriptions and flags; source/status; genres, platforms, categories, tags, developers, publishers, features, series, age ratings, and regions; cover/background/icon media and web links; custom game actions, library-plugin action policy, and ordered ROM records; installation state/directory/size, version/manual/HDR, runtime statistics; and pre/post/game-started scripts with their global-script policies. All four action types are editable, including emulator/profile selection, scripts, arguments, working directories, process tracking, timing, and emulator argument overrides. Local media is copied into a game-owned Core database path, replaced files follow Core cleanup, and HTTP/HTTPS background references remain remote. Bulk mode requires explicit per-field opt-in, gives each game independent action/link/ROM collections, and buffers all Core updates so unselected fields remain untouched. The same surface fulfills both plugin `OpenEditDialog` overloads. Manual add stages a default-status Core game in that full editor, joins and selects the live wrapper only after a valid save, and removes the provisional database record without residue on cancel. A native automatic-metadata overlay reuses Core `MetadataDownloader` for selected, filtered, or all games; persists source and field selection, skip-existing, and background-ingestion policy; exposes progress and cancellation; and imports HTTP cover/icon files into game-owned database storage. A native library-update overlay invokes Core `GameDatabase.ImportGames` for selected loaded integrations, supports all playtime import modes and customized plugin import paths, and also runs saved Core `GameScanner` configurations with their emulator/profile, ROM exclusion, platform/region discovery, relative-path, and default-completion-status behavior. It persists integration and scanner selection, optionally runs the same metadata pipeline for new games, exposes progress/cancellation/errors, synchronizes added and changed records into the live Desktop collection, and notifies plugins through `OnLibraryUpdated`. A separate installed-game overlay detects Start Menu and Microsoft Store programs, recursively scans folders, accepts individual `.exe`, `.bat`, and `.lnk` files through native pickers, filters existing launch identities, preserves Store/source and Windows-platform metadata, creates `{InstallDir}`-relative actions, extracts executable/resource icons into game-owned storage, applies default completion status, optionally downloads metadata, refreshes the live library, and notifies plugins. A native settings chooser now routes the public plugin settings API into an isolated Windows-only WPF compatibility host, preserving existing plugin views and the complete `ISettings` edit, validation, save, and cancellation lifecycle without bringing WPF into the Avalonia shell. Core retains legacy settings, custom-element, and converter registrations, and Avalonia theme markup can resolve existing WPF converters through a lazy adapter. Themes can declare `<foundation:PluginElementHost Plugin="SourceName" Element="ElementName" GameContext="{Binding Game}" />`; it resolves registrations loaded after the loose theme, embeds the existing WPF control in an owned child HWND, forwards `PluginUserControl.GameContext` updates without recreating the control, and destroys the native host with the Avalonia visual. Existing plugin web views run through the shared Avalonia WebView2 adapter for navigation, scripts, cookies, synchronous dialogs, and page inspection. Legacy static resources now bridge Avalonia localization into SDK `ResourceProvider` calls, supply the WPF theme primitives plugins commonly use during construction, and merge each extension's selected loose localization dictionary before instantiation. Fullscreen and Desktop share application host services through `Playnite.Avalonia.App`.

The installed-profile checkpoint loaded every available local extension from an isolated copy of a 21-game library: IGDB metadata 2.13 loaded its real settings model/view and declared metadata fields; a clean warnings-as-errors, audited rebuild of the official Steam integration source against AngleSharp 1.5.2 loaded its library API and real settings model/view. The installed Steam 2.40 binary itself still targets vulnerable AngleSharp 0.9.9 and must be republished by the extension ecosystem; the host neither restores that package nor hides the incompatibility. The compatibility report records both manifest and assembly versions so rebuilt test artifacts cannot be mistaken for untouched installed binaries.

Desktop and Fullscreen now share the Avalonia theme API 3 package model and cross-platform create/validate/pack tool. Desktop supports packaged and raw custom themes transactionally and publishes its stable resource and template-part contract in `THEME-MIGRATION.md`. The WebView2 bridge is Windows-native rather than cross-platform, and SDK v6 response-body interception has no equivalent in its common API. Script and HDR values now persist, but the shared Avalonia action runner still needs legacy script/HDR execution policy parity.
