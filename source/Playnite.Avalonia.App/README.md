# Shared Avalonia application host

`Playnite.Avalonia.App` contains application-level services shared by the side-by-side Avalonia Fullscreen and Desktop pilots. It adapts `Playnite.Core` game actions, extensions, notifications, dialogs, settings, and plugin APIs without depending on either shell's view models or theme.

Compiled SDK v6/WPF extensions continue through Core's existing collectible load context. Compiled SDK v7/Avalonia extensions are identified from assembly metadata before Core loading and are hosted side by side through `Playnite.SDK.V7.Host`, with a separate collectible load context and SDK v7 assembly instance for each extension. The SDK v7 host contract covers construction, settings serialization, paths and application information, resources, notifications, dialogs, game-operation dispatch, and application start/stop lifecycle. Its typed database transport maps every `IGameDatabaseAPI` collection and model across the isolation boundary, including CRUD, buffering, filtering, game import, database-owned files, and collection/open events. Play/install/uninstall controllers are adapted into the shared Core action runner with completion/cancellation signaling and the full game-operation event sequence. SDK v7 library plugins participate in Desktop's standard and customized import flows through Core's existing exclusion, update, playtime, file, and completion-status rules; their icons/backgrounds, client open/shutdown support, cancellation, and library-updated lifecycle are bridged as well. Dedicated v7 metadata plugins and official library metadata providers use Core's existing field/source selection, database-object resolution, image persistence, cancellation, and provider-disposal pipeline. Web-view and custom-UI parity is implemented in subsequent Phase 6 milestones.

Shell-specific behavior is supplied through `AvaloniaHostCallbacks`, `IAvaloniaHostSettings`, and `IAvaloniaDialogService`. Desktop supplies an Avalonia-native single- and multi-game editor to the shared plugin API callback. The WPF applications remain the production paths while these adapters are hardened.

Plugin web views use the maintained `Avalonia.Controls.WebView` adapter (WebView2 on Windows). The shared host supports visible and hidden views, synchronous dialog behavior, navigation/loading events, page text/source, JavaScript values and failures, custom user agents, and cookie management. Two SDK v6 contracts deliberately fail with precise compatibility errors instead of being ignored: `IWebView.WindowHost` is typed as a WPF `Window`, and Avalonia's common WebView API does not expose completed response metadata/body streams for `ResourceLoadedCallback`. The latter also leaves the Core DuckDuckGo response-interception path for the SDK v7 web contract.

Existing WPF plugin settings views, custom controls, and converters are isolated behind `Playnite.WpfPluginSupport`; the application surfaces and settings chooser remain native Avalonia.

The shared `GameActionRunner` preserves the legacy launch lifecycle for both shells: extension startup cancellation; global and per-game pre/start/post PowerShell stages with Playnite API, game, action, ROM, process, and mutable starting-argument variables; transactional runtime cleanup; system-HDR enable/restore across overlapping controlled games; plugin stop callbacks; and delayed, cancellable library-client shutdown. Shell JSON settings provide `GlobalPreScript`, `GlobalGameStartedScript`, `GlobalPostScript`, `ShutdownLibraryClients`, `ClientShutdownGraceSeconds`, `ClientShutdownMinimumSessionSeconds`, and `ClientShutdownPluginIds`. Client IDs are library-plugin GUIDs whose SDK properties advertise `CanShutdownClient`.
